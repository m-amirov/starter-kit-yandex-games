# Migration 0.4.1 — Target-aware updater

## Safety notice for 0.4.0

Starter Kit 0.4.0 is safe as a new-project source when its init checks pass, but
its updater is **unsafe for mature-project update without the 0.4.1 updater**.
The 0.4.0 manifest treated `index.html` and `AGENTS.md` as managed, delivered
skills only to `.codex/skills`, and offered generic product seeds during an
update.

The 0.4.0 path helper also used `URL.pathname`. On Windows a module URL such as
`file:///E:/Work/...` became `/E:/Work/...`, and `path.resolve()` produced the
invalid path `E:\E:\Work\...`. Version 0.4.1 uses
`fileURLToPath(import.meta.url)` before `path.dirname()`.

## Ownership and profiles

Manifest schema 2 requires one of these ownership classes:

- `managed`;
- `project-owned`;
- `semantic-merge`;
- `new-project-seed`;
- `target-mapped`;
- `ephemeral`.

Use `--profile new-project` only with `init`. Use
`--profile mature-yandex-phaser` for an existing Phaser/Yandex project. A custom
profile may be supplied as an absolute JSON path. Update of a non-empty target
without a stored or explicit profile is rejected.

The mature profile keeps `src/**`, `public/**`, `index.html`,
`project.profile.yaml`, and `game-spec.yaml` project-owned. Seeds are excluded
from update mode.

## Skill root mapping

Skills have stable logical IDs and target templates. The mature Phaser profile
maps the Starter Kit source `.codex/skills/<name>/...` to
`.agents/skills/<name>/...`. A second active skill root is rejected when
`allowSecondSkillRoot` is false.

## Semantic merge

`AGENTS.md`, project-wide Yandex contracts, `package.json`, and an existing
same-name skill are never overwritten. The updater writes the proposed source
to:

`.starter-kit/conflicts/<version>/<target>.new`

and human-readable instructions to:

`.starter-kit/conflicts/<version>/<target>.merge.md`

After a manual merge, record explicit acceptance with:

```bash
node tools/starter-kit/apply-update.mjs --target <project> \
  --profile mature-yandex-phaser \
  --resolve-semantic <logical-id>
```

## Safe workflow from 0.4.0

1. Start from a clean project revision.
2. Use the 0.4.1 updater, not the copied 0.4.0 updater.
3. Run an explicit mature-profile dry run.
4. Review every project-owned, mapped, and semantic-merge target.
5. Apply without automatic conflict acceptance.
6. Merge each proposal manually and record explicit resolution.
7. Run status and project-specific Yandex gates.
8. Roll back through Git if the plan or applied infrastructure is incorrect.

Dry run performs no writes. Neither dry run nor update creates a target-project
release ZIP. Installing infrastructure never assigns Yandex compliance `PASS`
and never changes product runtime automatically.
